# Simple Vault — практика Anchor

Учебный контракт на Anchor 0.31.1 (Solana). Полнофункциональное хранилище ликвидности.

## Недели 8, 9 и 10: Архитектура, Депозиты, Вывод и CPI

Контракт предоставляет 4 основные инструкции:
1. `initialize_vault` — инициализация хранилища и SPL-минтов (Неделя 8).
2. `create_user_card` — создание персональной карточки пользователя (Неделя 8).
3. `deposit` — внесение средств и выпуск share-токенов через CPI (Неделя 9).
4. `withdraw` — сжигание shares и вывод базовых токенов через CPI (Неделя 10).

---

### 1. Архитектура PDA и Сиды

- **PDA (Program Derived Address)** — детерминированные адреса, вычисляемые из сидов и Program ID, не имеющие приватного ключа и контролируемые программой.
- **Сиды хранилища (`vault_state`)**: `[b"vault", token_mint]`
- **Сиды токен-аккаунта хранилища**: `[b"vault_tokens", token_mint]`
- **Сиды минта долей**: `[b"share_mint", token_mint]`
- **Сиды карточки (`user_card`)**: `[b"user_card", vault, user]` (строго один аккаунт на пользователя в данном vault).

---

### 2. Формулы Shares, Депозита и Вывода

- **Депозит**:
  - Первый вкладчик: `shares = amount` (1:1).
  - Последующие: `shares = amount * total_shares / total_tokens`.
  - При наличии прибыли в пуле ценность доли растет (`total_tokens / total_shares > 1`), поэтому поздний вкладчик получает меньше shares за ту же сумму.

- **Вывод (Withdraw)**:
  - Формула:
    ```
    tokens_out = shares_amount * total_tokens / total_shares
    ```
  - Пользователь возвращает определенное число долей `shares_amount` и забирает причитающуюся ему долю всех базовых токенов в пуле (включая накопленный доход).

---

### 3. CPI и вывод из Vault (Неделя 10)

При вызове инструкции `withdraw` происходят два встречных межпрограммных вызова:

1. **Сжигание share-токенов (`token::burn`)**:
   - Вызывается SPL Token program через `CpiContext::new`.
   - Аккаунт: `user_share_account`.
   - Authority: сам пользователь (`user`). Пользователь авторизует уничтожение своих долей личной подписью транзакции.

2. **Перевод токенов из хранилища (`token::transfer`)**:
   - Вызывается SPL Token program через `CpiContext::new_with_signer`.
   - Источник: `vault_token_account`.
   - Получатель: `user_token_account`.
   - Authority: `vault_state` PDA.
   - Поскольку у `vault_state` нет приватного ключа, подпись генерируется с использованием сидов:
     ```rust
     let seeds = &[
         b"vault".as_ref(),
         token_mint_key.as_ref(),
         &[vault.bump],
     ];
     let signer = &[&seeds[..]];
     ```
   - Это гарантирует, что средства из хранилища могут быть переведены только по строгим правилам смарт-контракта.

3. **Inner Instructions в Solana Explorer**:
   - В модели Solana транзакция содержит одну или несколько инструкций верхнего уровня. Когда инструкция контракта вызывает другую программу через CPI (`invoke` или `invoke_signed`), эти вложенные операции регистрируются в рантайме как **Inner Instructions** (внутренние инструкции).
   - В Solana Explorer при просмотре транзакции `withdraw` видно:
     - Основная инструкция: `simple_vault: withdraw`
     - Вложенные Inner Instructions:
       1. `spl-token: burn` (сжигание shares)
       2. `spl-token: transfer` (перевод токенов из vault PDA пользователю)
   - Это обеспечивает прозрачный аудит всех перемещений средств и демонстрирует мощь атомарной компонуемости (composability) на Solana.

## Неделя 11 — AMM и концентрированная ликвидность (Raydium CLMM)

В рамках недели 11 изучаются принципы работы современных Automated Market Makers (AMM) и концентрированной ликвидности (Concentrated Liquidity Market Maker — CLMM) на базе протокола **Raydium CLMM** в сети **Solana Devnet**.

---

### 1. Традиционный AMM vs Концентрированная ликвидность

1. **Традиционный AMM (Constant Product, $x \cdot y = k$):**
   - Ликвидность распределена равномерно по всей числовой оси цен: от $0$ до $+\infty$.
   - Подавляющая часть капитала простаивает на ценовых уровнях, которые рынок может не достигнуть никогда.
   - Низкая эффективность капитала (Capital Efficiency) и высокое проскальзывание (slippage) при крупных сделках.

2. **Концентрированная ликвидность (CLMM):**
   - Поставщик ликвидности (LP) выбирает конкретный рабочий интервал цен $[P_{lower}, P_{upper}]$.
   - Все предоставленные средства работают исключительно внутри этого интервала.
   - Эффективность использования капитала возрастает в десятки и сотни раз по сравнению с классическим пулом.
   - **Особенность:** если рыночная цена выходит за пределы диапазона, позиция на 100% конвертируется в один из активов (наименее ценный в данный момент) и временно перестает зарабатывать торговые комиссии до тех пор, пока цена не вернется в диапазон либо позиция не будет переоткрыта (ребалансирована).

---

### 2. Дискретизация цен и математика тиков (Tick Math)

В архитектуре Raydium CLMM непрерывный ценовой график разбивается на дискретные ценовые интервалы — **тики (ticks)**.

#### Формула тика:
$$P(i) = 1.0001^i$$
где $i$ — целочисленный индекс тика (`i32`). Каждый тик соответствует изменению цены ровно на 1 базисный пункт ($0.01\%$).

#### Формат $Q64.64$ и $\text{sqrt\_price\_x64}$:
Для того чтобы блокчейн Solana мог производить детерминированные и высокоточные математические вычисления без использования медленных операций с плавающей точкой, цена хранится в виде квадратного корня, умноженного на $2^{64}$:

$$\text{sqrt\_price\_x64} = \left\lfloor \sqrt{P} \cdot 2^{64} \right\rfloor$$

Пример для цены $P = 2.0$:
$$\sqrt{2.0} \approx 1.41421356...$$
$$\text{sqrt\_price\_x64} = \lfloor 1.41421356... \times 18446744073709551616 \rfloor = 26087635650863001600$$

#### Шаг тиков (Tick Spacing):
В зависимости от пула и уровня торговой комиссии (Fee Tier) тики группируются с определенным шагом `tick_spacing`:
- Для пулов с комиссией $0.25\%$ шаг равен `60`.
- Для пулов с комиссией $0.05\%$ шаг равен `10`.
Все границы открываемых позиций (`tick_lower` и `tick_upper`) обязаны быть строго кратны `tick_spacing`.

---

### 3. Выбор диапазона тиков: почему $\pm 10\%$?

Для тестовой позиции выбран диапазон $\pm 10\%$ вокруг начальной цены:
- **Слишком узкий диапазон (например, $\pm 1-2\%$):** генерирует максимальную доходность на капитал, однако при малейшем рыночном импульсе цена покидает интервал, позиция отключается и требует постоянных ручных расходов на транзакции ребалансировки.
- **Слишком широкий диапазон (например, $\pm 50-100\%$):** работает пассивно, но размывает ликвидность и нивелирует ключевые преимущества CLMM.
- **Диапазон $\pm 10\%$:** является золотой серединой — обеспечивает высокую концентрацию капитала вблизи текущей цены и гарантирует, что типовые торговые свопы (включая задания 12-й недели) исполняются внутри активной ликвидности без риска вылета цены.

---

### 4. Архитектура аккаунтов Raydium CLMM

| Аккаунт | Назначение |
|---|---|
| `PoolState` | Главное состояние пула: адреса токенов, текущий тик, `sqrt_price_x64`, активная ликвидность, накопленные комиссии. |
| `AmmConfig` | Параметры протокола: ставка комиссии (`tradeFeeRate`) и шаг тиков (`tickSpacing`). |
| `TickArray` | Массив данных тиков, хранящий информацию о чистой ликвидности (`liquidityNet`), пересекаемой при движении цены. |
| `ObservationState` | Оракул скользящей средней цены (TWAP), обновляемый при каждом обмене. |
| `PersonalPosition` | Аккаунт конкретной позиции пользователя/vault, привязанный к уникальному Position NFT. |

## Неделя 12 — Swap через Raydium CLMM (CPI)

В рамках недели 12 реализована интеграция контракта Vault со смарт-контрактом **Raydium CLMM** через механизм **Cross-Program Invocation (CPI)**:
- Авторизованный обмен токенов хранилища через пул Raydium.
- Защита от проскальзывания цен (**Slippage Protection**).
- Архитектура **Strategy PDA** для безопасной фиксации целевого пула.

---

### 1. Архитектура Strategy PDA

Для расширения функционала хранилища без нарушения детерминированных адресов недели 8/9/10 добавлен отдельный аккаунт стратегии:
- **Seeds:** `[b"strategy", vault_state.key()]`
- Хранит:
  - `vault`: публичный ключ хранилища.
  - `pool`: адрес пула Raydium CLMM, с которым разрешено взаимодействовать.
  - `second_mint`: адрес второго токена торговой пары (`tUSD`).
  - `second_token_account`: токен-аккаунт хранилища под второй токен (`seeds = [b"vault_tokens_2", vault_state.key()]`, authority — `vault_state` PDA).

> 🔒 **Безопасность:** Администратор не имеет права менять токены через произвольные сторонние пулы. Инструкция `swap_raydium` принудительно сверяет переданный пул с записанным в `Strategy` (ошибка `WrongPool`).

---

### 2. Схема межпрограммного вызова (CPI Flow)

```
[ Администратор ]
        │  1. swap_raydium(amount_in, min_amount_out)
        ▼
[ Simple Vault Program ]
        │
        │  2. Валидация прав администратора и Strategy Pool
        │  3. Генерация подписи PDA сидами: [b"vault", token_mint, bump]
        │  4. raydium_clmm_cpi::cpi::swap_v2
        ▼
[ Raydium CLMM Program ]
        │
        │  5. Перевод input токенов из vault_tokens -> pool_vault
        │  6. Проход по TickArray, расчет цены исполнения и комиссий
        │  7. Проверка slippage: actual_out >= min_amount_out
        │  8. Перевод output токенов из pool_vault -> vault_tokens_2
        ▼
[ Результат: Атомарный обмен с защитой от фронтраннинга / сдвига цены ]
```

---

### 3. Защита от проскальзывания (Slippage Control)

При обмене в пулах с концентрированной ликвидностью цена непрерывно изменяется при пересечении тиков. Для защиты средств вкладчиков используется параметр:
```rust
other_amount_threshold: min_amount_out
```
- Если рыночная ликвидность недостаточна или в момент подтверждения транзакции цена сдвинулась и выходная сумма оказалась меньше `min_amount_out`, транзакция **полностью отменяется** смарт-контрактом Raydium (`TooLittleOutputReceived`).
- Средства хранилища остаются нетронутыми.
